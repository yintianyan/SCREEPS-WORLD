# 30 · 架构红队评审（Red Team Review）

> 总任务书 §30 要求：完成第一版架构后必须主动攻击自己的设计。评审对象：
> [26_FINAL_ARCHITECTURE.md](26_FINAL_ARCHITECTURE.md) + [ARCHITECTURE_DECISIONS.md](ARCHITECTURE_DECISIONS.md)
> 全部 12 条 ADR。评审日：2026-08-22。攻击维度覆盖任务书清单：性能瓶颈 / 架构
> 死锁 / 状态冲突 / 优先级 / CPU 爆炸 / Memory 爆炸 / 帝国扩张后 / PvP / 多房间 /
> RCL1 自举 / RCL8 后期。

## 1. 方法论

每条攻击给出：攻击点 → 场景推演 → 裁决（**成立 / 部分成立 / 不成立**）→ 修订
（落点）。裁决标准：能在既有框架内修复的记「成立（可修复）」；推翻 ADR 的记
「成立（架构级）」——本次评审结论：**无架构级推翻，6 条可修复攻击成立**，
全部转化为实现级硬约束。

## 2. 攻击清单

### A1 · CPU 爆炸：帝国战略层每 tick 全量态势聚合
**推演**：50 房帝国，战略层每 tick 聚合全部房间的能量/威胁/CPU 数据 → 每房间
哪怕 0.02 CPU 的聚合成本，乘 50 房再乘每 tick，就是持续性底噪；态势聚合里任何
一次全量 `find`/对象枚举都是数量级放大。
**裁决**：成立（可修复）。
**修订**：战略层输入（EmpireSituation）必须**分频聚合**（N tick 全量 + 每 tick
增量），且战略层本身以「态势快照未刷新则沿用上次决策」为默认语义——决策函数
天然幂等，快照过期不重算。落点：26 §3 步骤 3、20 号三档节奏判据。

### A2 · 恢复风暴：Recovery 档砍远矿后的重启冲击
**推演**：CPU 紧张 → Recovery 砍掉全部远矿 → 远矿 creep 老死（1,500 tick）→
CPU 恢复 → 6 条远矿车道同时重启，每条要 spawn 3–4 只 creep + 重建 container →
能量与 spawn 队列瞬时冲击，可能把刚恢复的经济再次压垮（二次降级振荡）。
**裁决**：成立（可修复）。
**修订**：远矿恢复必须**分批节流**（每 N tick 恢复一条车道，或按 CPU 余量逐条
解锁）；远矿重启是 Agenda 项，天然支持预算与节奏控制。落点：17 号自举车道 +
27 号 P5 验收增加「恢复期无二次降级」指标。

### A3 · 姿态振荡：war↔fortify 死循环
**推演**：被打 → war（暴兵）→ 经济压力超标 → fortify（收缩）→ 压力缓解+还在
被打 → war……若滞回窗口短于战争波次周期（集结+推进+战后核验），系统在两个
姿态间打摆，每次切换都作废上一波次的投入。
**裁决**：成立（可修复）。
**修订**：**war 退出的滞回窗口 ≥ 一个完整波次周期**（集结时间 + 推进时间 +
核验时间）；姿态切换带 minDuration 承诺（07 号三重防线已建，红队钉死参数
约束：minDuration 由波次周期推导而非拍脑袋）。落点：06 号 posture 表 + ADR-009。

### A4 · 写者越权回归（工程纪律风险）
**推演**：三个月后新增一个角色，开发者图省事在 work 钩子里全房 `find` + 直接
发 spawn 请求——架构防线是文档约定，运行时无人拦截。
**裁决**：部分成立（工程风险，框架无法完全消除）。
**修订**：静态检查（lint 规则禁 `Room.find` 于角色目录）+ 运行时断言（组合根
注册时校验 Policy 钩子签名）+ code review 清单项。落点：29 号 R-12 防线具体化。

### A5 · 单点熔断：spawn manager 进入冷却
**推演**：spawn manager 连续异常 3 次 → 熔断 50–200 tick → 全帝国停产，灾后
恢复窗口正好是人口断档的开始。
**裁决**：部分成立（规则已有，边界必须显式化）。
**修订**：**spawn manager 属 P0，永不熔断**（错误隔离照常，但冷却跳过）；同时
紧急车道（≥200 能量立即 [WORK,CARRY,MOVE]）做成内核级直通路径，不依赖任何
P1+ 系统健康。落点：22 号熔断器 + 19 号 P0 语义。

### A6 · 迁移中断：分 tick 迁移中途 global reset
**推演**：大迁移按 cursor 分 tick 执行到一半 → global reset（heap cursor 丢失）→
重入时从头再来或半迁移状态。
**裁决**：成立（规则已覆盖，红队确认必要性）。
**修订**：迁移游标与完成标记必须存 **Memory**（非 heap）；每步幂等（重复执行
同一步无副作用）；schemaVersion 只在全部步骤成功后更新。落点：18 号迁移规范
（该文档已按此约束书写，此处为红队确认记录）。

### A7 · 情报欺骗：伪装安全诱捕扩张
**推演**：宿敌清空目标房驻军 → 我方 intel TTL 内看到「无人房」→ 扩张尽调通过 →
殖民车队进入 → 宿敌回兵收割。PvP 对抗演化无法靠静态规则穷尽。
**裁决**：成立（可缓解，不可根除）。
**修订**：扩张尽调要求**多源新鲜度硬门槛**（scout 亲见 + 时间窗 + 邻接房无
敌踪）；殖民自举带武装护航可选项；战损超过阈值立即降级撤离（17 号失败降级表）。
**残余风险**：对抗演化依赖战争账本事后复盘闭环（16 号），记入 29 号 R-15。

### A8 · 仲裁瓶颈：tick 末集中交通仲裁
**推演**：200 creep 在同一房 → 意图冲突检测 O(n²) → tick 末 CPU 峰值。
**裁决**：成立（可修复）。
**修订**：交通仲裁**按房分桶**（房间间独立），房内用意图网格索引（位置→意图
哈希）把冲突检测降到近似 O(n)。落点：26 §3 步骤 7 约束。

### A9 · RCL1 自举死锁：请求池物流空转
**推演**：bootstrap 期没有 container/storage，物流请求池没有供给侧 → hauler
空转或请求池死循环。
**裁决**：不成立。
**理由**：bootstrap phase 的声明式形态是「harvester 直供 spawn/extension」
（10 号 phase0 人口结构 + 27 号 P2 交付），请求池物流在 storage 经济建立后才
接管；phase 模型保证了两种形态不混用。

### A10 · RCL8 动能丧失：合理停滞被误诊
**推演**：RCL8 + GCL 满 + 市场饱和 → 一切指标「停滞」→ 自愈系统把健康房间的
停滞误诊为故障，反复触发「恢复动作」（重启车道/重建缓存）反而制造波动。
**裁决**：成立（可修复）。
**修订**：Verification 步骤必须对照**预期状态**（「后期稳态」是合法状态）；
后期需要显式 energy sink 目标集（GCL farm/temple/power，10 号清单），让「有
事可做」而非靠停滞检测驱动。落点：22 号 Verification 语义 + 10 号 sink 清单。

### A11 · 多房同时被袭：资源争抢与 safemode 抉择
**推演**：两房同时 siege → 各自独立响应 → spawn 能量与增援互相争抢；两房同时
满足 safemode 触发条件，但每 shard 只允许一房开启。
**裁决**：成立（可修复）。
**修订**：战时资源仲裁上收帝国层（04 号下发接口的战时语义）；safemode 决策表
必须含多房同时候选的优先序（可保住的房子优先：能量储备+防御完整度评分）。
落点：15 号 safemode 决策表。

### A12 · 市场重复成交
**推演**：两个系统同 tick 对同订单 `deal` → 重复扣款（每 tick 10 笔限额内完全
可能发生）。
**裁决**：成立（规则已覆盖，确认唯一写者 + 幂等键 + 成交核验三件套缺一不可）。
落点：ADR-010 相邻的市场唯一写者约束（26 §3 写者模型）。

## 4. 结论

1. **12 条 ADR 全部幸存**——攻击未发现需要推翻的架构裁决；轻量内核、两级决策、
   姿态×预算、唯一写者模型在攻击下表现出可修复性（修复都在参数与实现约束层）。
2. 最危险的三个攻击是 A2（恢复风暴）、A3（姿态振荡）、A10（停滞误诊）——共同
   特征：**系统的自愈与自适应机制本身成为振荡源**。这是自治系统的共性风险，
   防线原则统一为「任何自动切换都带承诺期与预期状态核对」。
3. PvP 对抗演化（A7）是唯一无法静态根除的残余风险，依赖战争账本复盘闭环
   （16 号）持续迭代——记入 [29_RISK_REGISTER.md](29_RISK_REGISTER.md) R-15。
4. 本评审的 12 条修订约束已回写进对应文档（见落点列），26 号总纲引用本文件
   作为修订记录。
