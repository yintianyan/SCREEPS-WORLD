## 一、问题本质分析

这个项目已经远超 plan.md §6 中定义的 M6 里程碑，实际进度覆盖了 M7-M8 的大部分内容（link、lab、tower 防御、min-cut 防御规划、pixel 生成、遥测时序、参数自调优），但 **plan.md 停留在 M6 的设计文档状态**，导致文档与代码之间产生了系统性偏差。

## 四、P1 架构问题（本周修）

### P1-1：O(rooms × creeps) 重复遍历 — 多房扩展瓶颈

**spawn-manager.ts** 第 38-39 行：

```ts
for (const snapshot of ctx.snapshots()) {
  const creeps = collectCreepSummaries();    // ← 遍历全部 Game.creeps
  const spawning = collectSpawningSummaries(); // ← 遍历全部 Game.spawns
```

`collectCreepSummaries()` 在 **每个房间的循环内** 调用，遍历全部 `Game.creeps`。N 个房间 × M 个 creep = **O(N×M)** 每 tick。

`assignment-service.ts` 第 88 行同样的模式：

```ts
for (const snapshot of ctx.snapshots()) {
  // ...
  for (const creep of Object.values(Game.creeps)) { // ← 每房间一次全量遍历
```

**当前影响**：1 房间 × ~15 creep = 15 次/tick，可忽略。
**10 房间影响**：10 × ~50 creep = 500 次/tick，在 20 CPU 下开始可感知。

**对比**：Kernel.buildSnapshots() 已经正确地在循环外预构建 `globalSourceOccupancy` 和 `globalCreepEnergy`。spawn-manager 和 assignment-service 应遵循同样的模式。

### P1-2：room-snapshot.ts 隐式耦合 movement 缓存

`room-snapshot.ts` 第 97-119 行直接写 `globalCache().__structCache`：

```ts
{
  const g = globalCache() as any;
  if (!g.__structCache) g.__structCache = {};
  // ... 直接构建 movement.ts 的结构缓存
  g.__structCache[room.name] = { count, positions, checkedTick: Game.time };
}
```

**问题**：
- `room-snapshot` 隐式知道 `movement.ts` 的内部缓存结构
- 使用 `as any` 绕过类型安全
- 如果 `movement.ts` 缓存结构变化，`room-snapshot` 不会得到编译错误
- 违反"每个模块拥有自己的数据"原则（plan.md §2.3）

**正确做法**：movement.ts 应暴露 `preloadStructureCache(room, allStructures, mySites)` 函数，room-snapshot 调用它。

### P1-3：tower-defense.ts hasRepairCreep 隐式全局扫描

`tower-defense.ts` 第 105-119 行：

```ts
function hasRepairCreep(roomName: string): boolean {
  const g = globalCache() as any;
  if (g.__repairCreepTick !== Game.time || !g.__repairCreep) {
    // 遍历全部 Game.creeps 检查 builder/worker 存在
    for (const creep of Object.values(Game.creeps)) { ... }
  }
}
```

**问题**：
- 塔防系统（P0）在维修逻辑中遍历全部 Game.creeps
- 虽有 per-tick 缓存，但首次调用仍是全量扫描
- 应从 RoomSnapshot 获取此信息（snapshot 已有结构数据，creep 数据可通过 sourceOccupancy 模式预构建）

### P1-4：tuning-engine.ts 死代码

`tuning-engine.ts` 第 79 行：

```ts
const currentBounds = getRoleBounds("", roomName); // ← 结果从未使用
```

这行代码获取了 `currentBounds` 但后续从未引用——真正的 bounds 获取在下面的循环中（第 82-84 行）。这是开发过程中遗留的调试代码。

### P2-5：economyPressure — 代码中广泛使用但 plan.md 未定义

- `demand.ts`：梯度缩放 upgrader/builder 数量
- `tuning-engine.ts`：调优信号

plan.md 中完全没有这个概念——它仍使用二值 `crisis/normal` 开关的描述。这是 **代码比 plan.md 更优** 的典型案例：梯度信号比二值开关更平滑，避免了抖动。

`domain/economy/phase.ts` 实现了殖民相位系统（growth/stable/surplus/crisis/recovery），带迟滞的状态机。`room-state.ts` P0 系统每 tick 运行它，将相位映射为 ColonyState。

## 七、Memory 迁移系统审查 — 无双轨运行问题

### 7.1 迁移链路完整性

```
v0 → v1: 初始化 creeps/rooms
v1 → v2: 添加 kernel/队列/layout，迁移 working→mode
v2 → v3: 扩展 layout overrides/blocked
v3 → v4: layout 冷数据迁移到 RawMemory segment
v4 → v5: recycle/intel 字段自愈
v5 → v6: compact-core-v1 → v2 模板切换
v6 → v7: tuning Memory 结构自愈
```

每个迁移都是幂等的，重复执行不会产生副作用。`migrateMemory()` 在循环结束后强制 `Memory.schemaVersion = CONFIG.memory.schemaVersion`，确保版本不会卡住。

### 7.2 无双轨运行问题

**结论**：不存在双轨运行问题。迁移系统设计正确：
- 迁移按版本顺序执行，每步检查 `version === migration.from`
- 每步成功后更新 `Memory.schemaVersion`
- 最终强制设为目标版本
- 死 creep 清理在迁移后执行，不干扰迁移

唯一的风险是 **大迁移未按 cursor 分 tick**（plan.md §3.4 规范第 4 条）。当前所有迁移都是同步完成的，没有 cursor 机制。如果未来有需要分 tick 的大迁移，需要额外实现。

## 八、plan.md vs 代码 — 谁更优？

| 维度 | plan.md | 代码 | 更优者 | 理由 |
|------|---------|------|--------|------|
| 经济状态信号 | 二值 crisis/normal | 梯度 economyPressure (0.0-1.0) | **代码** | 梯度信号避免抖动，各子系统平滑缩放 |
| 殖民状态计算 | kernel.computeColonyState | room-state P0 系统 + ColonyPhase 迟滞 | **代码** | 迟滞状态机防止频繁切换，P0 每 tick 运行更及时 |
| 布局方案 | 纯模板 + relocation | constraint/template 双模式 | **代码** | constraint 模式从地形推导，适应不同房间 |
| 防御系统 | 单一 defense.ts | tower-defense(P0) + defense-planner(P3) + min-cut | **代码** | 攻击/维修(P0)与布局规划(P3)优先级分离更合理 |
| 角色实现 | 各角色独立状态机 | RolePolicy 声明式 + Action-Candidate 引擎 | **代码** | 新增角色只需声明 policy，无需复制生命周期代码 |
| 升级功率控制 | 固定数量梯度 | storage 水位 + RCL8 限速 + 大 body 站桩 | **代码** | 1 个 15W upgrader 顶满官方上限，省 CPU/spawn 窗口 |
| Spawn 需求 | 固定 DESIRED 数量 | 动态需求 + 梯度缩放 + 四重门禁替换 | **代码** | hauler 数量跟随 container 积压动态调整 |
| 参数调优 | 无 | tuning-engine 遥测驱动自调优 | **代码** | 系统自适应不同房间/经济状态 |
| 文档完整性 | §1-§11 完整设计 | 注释详尽但无总体文档 | **plan.md** | plan.md 的边界场景清单、风险表、测试策略无替代 |
| 迁移规范 | §3.4 明确规范 | 代码遵循规范但无文档 | **plan.md** | 迁移规范是防回归的必要文档 |

**结论**：**代码在实现层面全面优于 plan.md**，但 plan.md 在 **设计约束、边界场景、风险分析** 方面的价值不可替代。正确做法是 **更新 plan.md 以反映代码的实际架构**，而非让代码退回 plan.md 的旧设计。

## 十、CPU 热点评估

### 10.1 当前热点（从代码结构推断）

| 模块 | 每 tick 成本 | 说明 |
|------|-------------|------|
| `buildRoomSnapshot` | O(structures + sources + sites + hostiles) | 每房一次 find，不可避免 |
| `spawn-manager.collectCreepSummaries` | O(rooms × creeps) | **可优化**（P1-1） |
| `assignment-service.generateRoomTasks` | O(rooms × creeps) | **可优化**（P1-1） |
| `layout-planner` (P3, 每 50 tick) | O(cells × validation) | 已优化：预计算 structureCounts/occupiedSet |
| `tuning-engine` (P3, 每 500 tick) | O(economy samples + creeps) | 可忽略 |
| `Kernel.runCreeps` 排序 | O(creeps × log(creeps)) | 每 tick 排序，可缓存但当前规模可忽略 |

### 10.2 20 CPU 预算评估

**当前**（1 房间 ~15 creep）：估计 8-12 CPU/tick，在预算内。
**10 房间 ~50 creep**：P1-1 的 O(N×M) 问题会使 spawn-manager + assignment-service 的 CPU 翻 10 倍，可能从 ~1 CPU 涨到 ~5 CPU。修复 P1-1 后可控制在 ~2 CPU。
